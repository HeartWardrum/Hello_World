各位领导好。接下来由我我介绍一下《预授信额度动态测算项目技术需求文档》。

这份文档不是业务宣讲材料，而是一份可落地的技术规格。它规定了数据清洗、模型训练、线上打分的流程。主实现路径是路径 A，也就是用 Java 自己训练模型、自己预测额度。附录里还有路径 B，可以用 已有Python 产出可用的模型，再交给 Java 侧联调。

先说核心业务逻辑。系统对每一个客户做两件事，第一件事是前置模型，用 CART 决策树判断该户是否属于一千万及以上这一档；如果命中，前置建议额度固定为一千万。第二件事是额度模型，按四个可以重叠的客群分别建模，分别是一般客群、科技客群、外贸客群和制造业客群。每个客群一套 CatBoost 多分类模型，先预测额度区间，再换成具体金额，再做调额后处理。

**合并规则**是这样的。如果前置没有命中，最终建议额度就等于额度模型给出的调额后额度。如果前置命中了，最终建议额度取前置建议额度和调额后额度两者之中的较大值。文档特别强调一点：前置命中的客户仍然要进入额度模型，不要在额度阶段提前剔除，合并时再比较高低。另外，一户可以同时属于多个客群，就要分别跑、分别合并；如果需要多客群汇总，对同一个统一社会信用代码再取各客群最终建议额度里的最大值。

下面按文档结构说完整性。全文按实现顺序写，主要有六块，外加附录。第一章是总览，讲清两模型、四客群和合并口径。第二章是数据准备，讲从原始数据到训练宽表和打分宽表，包括清洗、长转宽、衍生财务比率、手工分箱、业务标签，以及入模开关和打分开关。第三章是训练规格，写死前置 CART、各客群 CatBoost、特征工程口径，以及产物目录约定。第四章是预测全过程，按顺序是读表筛选、前置预测、按客群做额度预测、调额后处理，再合并最终建议额度。第五章是联调验收清单，列出金额单位、列映射、产物成对使用、命中户仍进额度等硬性检查项。第六章是结论，并在附录 A 说明路径 B 的 Python 操作步骤。

从完整性看，输入规范、训练口径、推理流程、产物格式、验收清单和双路径说明都具备，能够支撑后续开发对照实现。从规范性看，关键约束写得很明确：金额统一为元，比率统一为小数；训练集用「是否进入模型」，打分集用「是否参与打分」，两个开关不能混用；训练阶段特征映射用二零二四年相关源列，打分阶段必须用二零二五年相关源列，增速类用二零二三到二零二五年，不能把训练年的列误接到打分上。这些写法有利于避免联调踩坑。

再说一下算法与后处理，方便大家判断技术可行性。前置侧大致是：先做特征工程，再做 Pipeline，数值列用中位数填补再做标准化，类别列用众数填补再做独热编码，然后送入 CART，用叶节点正类概率和阈值比较，达到阈值就命中并给出一千万。额度侧是把实际授信额度切成五个区间，边界是零、二百五十万、五百万、六百五十万、八百万、一千万，模型先出档位，再取该档代表金额。后处理按固定顺序连乘行业系数、高负债系数、增速分位系数、交叉比对系数，再乘全局调额系数，最后在档内做上下限钳制。产物方面，前置相关参数放在 gate 目录，各客群的 CatBoost 模型和预处理状态放在各自的 limit 目录；同一客群的模型和 JSON 必须来自同一次训练，禁止跨客群或跨批次混用。换客群或换期必须重训后再打分。

综合以上，这份技术需求文档结构完整、口径明确，能够指导开发和联调，满足交付要求里对技术文件完整性和规范性的审查，也能为后续内部开发提供参考依据。建议开发时优先对照第五章验收清单逐项核对，尤其注意三点：打分时不要误用训练开关；打分特征必须使用二零二五年源列；前置命中户仍然进入额度模型。
